# tools/dsp — coefficient format and fixed-point analysis for the ADAU1860

Two offline scripts that settle questions the DSP build spec in `docs/` and
the `TODO(hw-bringup)` comments in `src/adau1860_control.c` left open. No
hardware needed; everything here is derived from upstream OpenEarable 2.0's
published source (`OpenEarable/open-earable-2`, which drives this exact chip
on this exact board) plus the RBJ math the firmware already uses.

```sh
pip install -r requirements.txt
python3 coeff_format.py --json golden.json      # ~1 s
python3 fixed_point_notch.py --out results       # ~5 s; --quick for a coarse grid
python3 fdsp_bank_decode.py [path/to/Lark-fdsp.c]  # <1 s; FastDSP feedback-tap sign
```

Confidence labels below: **verified** = reproduced numerically from upstream
data to floating-point noise; **modelled** = a simulation whose assumptions
are stated and could differ from the real silicon.

## 1. Coefficient format — `coeff_format.py`

**Question.** The firmware's `calc_band_coeffs()` computes float RBJ biquad
coefficients and stops: the number format and slot layout the DSP wants were
listed as unknown ("8.24 fixed vs float core").

**Data.** Upstream's `src/audio/Equalizer.cpp` is a nine-row biquad table
where every row is annotated with its design parameters *and* its five hex
words — e.g. `{0x07ED1CFE, 0xF03F890A, 0x07D420FF, 0xF03F890A, 0x07C13DFD} // f: 150 G: -8.0dB Q: 1.0`.
Upstream's own comment on the table says "Fix point arithmetic 5.27", and
`ADAU1860::fdsp_set_volume()` safeloads `1 << 27` as unity into the FastDSP
VOLUME slot — so the table's format is also the FastDSP parameter format.

**Result (verified).**

| Fact | Value | Evidence |
|---|---|---|
| Number format | **Q5.27** two's-complement, 1.0 = `0x08000000` | Only format where any design formula reaches float-noise error across all 7 peaking rows (Q8.24 is off by ~14, Q1.31 by ~2) |
| Slot order | **[b0, b1, b2, a1, a2]**, a0 normalised to 1 | Direct decode |
| a1/a2 sign, software EQ table | **stored as-is** (H(z) denominator is 1 + a1 z⁻¹ + a2 z⁻²) | Negating a1/a2 raises the best-case error from 3e-9 to ~4 |
| a1/a2 sign, **FastDSP hardware slots** | **stored NEGATED**: slot = `[b0, b1, b2, -a1, -a2]` | `fdsp_bank_decode.py`: every shipped biquad in upstream's `Lark-fdsp.c` banks is stable (|pole| 0.77–0.998) only under the negated reading; as-is gives |pole| ≈ 1.7–2.4 |
| Generator | **Orfanidis** peaking EQ (JAES 1997, unity gain prescribed at Nyquist), fs = 48 kHz, Δω = ω0/Q, G_B = √G | All 7 rows match to ≤ 3.1e-9 |

**Why RBJ "drifts".** A plain RBJ-cookbook recomputation matches the 150 Hz
row to five decimals but is off by 0.17 at 13 kHz. That is not a format or
sample-rate problem — a per-row sample-rate fit under RBJ doesn't converge on
any common fs — it's that upstream's table was generated by the Orfanidis
design, which pins unity gain at Nyquist where RBJ's bandwidth warps. Both
designs realise exactly the annotated f0 and gain (the script measures the
words' actual response: 150.1 Hz/−8.00 dB … 13000.1 Hz/−6.00 dB). For Haven
this is a footnote: the firmware computes its own coefficients, so only the
*format* matters. (Orfanidis is arguably the better formula for Haven's
8 kHz upper band at 48 kHz, but the difference is immaterial at 192 kHz.)

**For the firmware.** `golden.json` carries the facts as data: encode with
`round(x * 2**27)` wrapped to uint32; unity biquad is
`{0x08000000, 0, 0, 0, 0}`; the 150 Hz row is a legitimate golden vector for an
RBJ-based encoder (low f0, so RBJ ≡ Orfanidis to 5 decimals); the other six
rows are Orfanidis-exact and must **not** be used as RBJ goldens. **Sign caveat:** the Equalizer.cpp table is upstream's nRF-side *software* EQ; the codec's FastDSP slots store the feedback taps negated (see the table above and `fdsp_bank_decode.py`), so an encoder targeting FastDSP must write `-a1, -a2` — and the 150 Hz golden's last two words must be negated (two's-complement) when used as a FastDSP golden. `golden.json` carries both conventions explicitly.

## 2. Q5.27 quantisation of Haven's notches — `fixed_point_notch.py`

**Question.** Upstream frame-clocks FastDSP from the DMIC stream at
**192 kHz** (`FDSP_CTRL4 = 2` → rate source DMIC01; `DMIC_CTRL2 = 0x04`).
The firmware's coefficient math assumes 48 kHz. Coefficients have to be
computed at whatever rate FastDSP actually runs — ADI's EVAL-ADAU1860 user
guide (UG-2017, p. 7) says exactly this of its own Lark Studio tool: *"set fs
to be the same as the FastDSP source, FDSP_RATE_SOURCE, which is set in the
FastDSP tab"*. Haven's narrowest band (Q = 20 at 200 Hz) at 192 kHz puts the
poles at radius 1 − 1.6e-4, which is where 32-bit fixed point could plausibly
bite. Does it?

**Grid.** f0 200–8000 Hz (25 log steps) × Q 1–20 (15 log steps) × atten
{40 (pure notch), 20, 6} dB × fs {48k, 192k}, RBJ formulas identical to
`calc_band_coeffs()`.

**Effect A — coefficient rounding alone (verified, exact arithmetic).**

| | fs = 48 kHz | fs = 192 kHz |
|---|---|---|
| Designs stable & representable | 375/375 at every atten | 375/375 at every atten |
| Min stability margin 1 − |pole| (Q=20, 200 Hz) | 6.5e-4 = **87 807 LSBs** | 1.6e-4 = **21 959 LSBs** |
| Worst centre-frequency shift | 0.012 cents (0.0014 Hz) | 0.20 cents (0.024 Hz) |
| Worst peaking-cut depth error (20 dB / 6 dB cut) | 0.0001 dB / 0.0000 dB | 0.0004 dB / 0.0001 dB |
| Pure notch: min depth at the *commanded* f0 | **75.9 dB** | **48.9 dB** |

The pure-notch row needs one comment: RBJ gives b0 = b2 exactly and rounding
preserves that, so the quantised zeros stay *on* the unit circle — the notch is
still infinitely deep, merely shifted by the Δf0 above. The finite number is
the depth at the frequency you asked for, and its worst case (200 Hz, Q = 20,
192 kHz) is 49 dB — still deeper than the 40 dB `PROTOCOL_ATTEN_MAX_DB` cap.

**Effect B — coefficient + 32-bit state rounding (modelled).** A direct-form-I
biquad with double-precision multiply-accumulate and Q5.27 rounding of the
output/state every sample, driven by a 0.25 FS tone at f0 plus a −40 dB tone
three bandwidths up. ADI does not document FastDSP's accumulator width, so
this is an order-of-magnitude model of "what if the datapath is only 32 bits",
not a bit-accurate simulation.

| design | realised att. @ f0, 48 k | 192 k | rounding-noise floor |
|---|---|---|---|
| 200 Hz, Q 20, full notch | 98 dB | **55 dB** | −88 dBFS (both) |
| 200 Hz, Q 20, 20 dB cut | 20.0 dB | 20.0 dB | −86 dBFS |
| 200 Hz, Q 1, full notch | 105 dB | 79 dB | −114 / −111 dBFS |
| 4500 Hz, Q 10, full notch | 134 dB | 128 dB | −122 dBFS |
| 8000 Hz, Q 20, full notch | 150 dB | 116 dB | −118 dBFS |

Side-tone attenuation matches the ideal to within the measurement's ~0.1 dB
window resolution in every case, i.e. the passband is not disturbed. The
−88 dBFS floor for the narrow 200 Hz notch is the classic low-frequency
high-Q recursive-noise amplification; it sits ~25 dB below what a MEMS mic
(~65 dB SNR) puts into the chain, so it is inaudible in this application.

Q1.31 is reported for completeness: it cannot represent |a1| ≈ 2cos ω0 > 1,
so 0/375 notch designs fit at 192 kHz without pre-scaling. Not applicable.

## Recommendation: which FastDSP rate

**Q5.27 is not a constraint at either rate.** Every Haven design is stable and
representable at both 48 and 192 kHz; centre-frequency shifts are ≤ 0.2 cents
(a fifth of a percent of a semitone); commanded cut depths are reproduced to
< 0.001 dB; even the worst pure notch keeps ≥ 49 dB at the commanded f0 with
coefficient rounding alone and ≥ 55 dB in the pessimistic 32-bit-state model,
against a product ceiling of 40 dB.

So the rate should be chosen on the non-numerical axis, and there the answer
is to **keep upstream's 192 kHz DMIC-sourced frame rate and compute Haven's
coefficients at 192 kHz** (`ADAU1860_SAMPLE_RATE_HZ` → 192000, or make it
track the configured `FDSP_CTRL4` source):

- It is the configuration upstream ships and has run on this board; a 48 kHz
  FastDSP would mean either inserting a FDEC decimation stage in front of the
  FastDSP input or switching `FDSP_CTRL4` to a fixed-rate source — new
  register-level work with no numerical payoff.
- Hear-through latency through the FastDSP frame is 1/fs: ~5 µs at 192 kHz vs
  ~21 µs at 48 kHz. Neither matters against the DMIC decimation/DAC
  interpolation delays, but 192 kHz is the direction that helps.
- What 48 kHz would buy is 4× more stability margin (88 k vs 22 k LSBs) and
  ~40 dB more depth on the single worst-case notch — margin Haven doesn't
  need.

One thing this analysis cannot settle: FastDSP has a fixed instruction budget
per frame, so a 192 kHz frame rate leaves 4× fewer cycles than 48 kHz.
Upstream's 12-instruction program (5 biquads + expander + volume + mute +
mixer + limiter) evidently fits, and Haven's program is the same shape, so
this is very unlikely to bind — but confirm it on hardware (or in Lark Studio,
which reports the cycle count) before adding stages.

## Limitations

- Effect B models a 32-bit DF-I datapath. If FastDSP keeps wider accumulators
  (typical for ADI DSPs) the real numbers are better than shown; if it uses a
  different topology (DF-II/transposed) the noise distribution differs. The
  conclusion ("not a constraint") is robust to this; the exact dB figures are
  not.
- Side-tone attenuation is measured with a Hann window over a 0.34–0.68 s
  segment; treat differences under ~0.15 dB as measurement noise.
- Nothing here has been checked against the ADAU1860 datasheet PDF, which was
  not fetchable from the environment this was written in; the register-level
  facts (FDSP_CTRL4 rate source, 1<<27 unity) come from upstream's driver and
  UG-2017.
